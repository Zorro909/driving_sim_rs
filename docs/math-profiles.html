Math profiles

Historical design draft for issue #7, based on code at e96a2e8 and the 56-build UCRT survey. The original proposal and diagrams below are retained as design history.

Implemented profiles

The implementation supports proton, win10-fma3 and win11-fma3. Every native/WASM/GPU build includes all three. Defaults detect the host's operating system and version; resumed runs retain their saved profile. SSE2 variants are outside the supported scope.

The new Windows kernels share restricted C source in math/kernels/ucrt.h, translated to Rust/WASM and WGSL and included by HIP/CUDA. The established musl and AVX2 ports remain. WebGPU pipeline creation specializes the generated module for the session's profile. Current kernel, fixture and verification documentation describes the implemented architecture.

Original proposal

TL;DR
  • Make the platform's C runtime a runtime parameter (MathProfile) instead of a fact baked into every backend. Five profiles cover everything we measured: Proton and four Windows ones.
  • Write each math variant once, in the restricted C subset that gpu/sim/*.h already uses, and generate the Rust, AVX2, HIP and WGSL versions from it. This extends the existing gen-sim.py / gen_tables.py pipeline instead of adding a new one.
  • Use exception tables where exhaustive proof is possible (sinf/cosf: every float32 can be checked, as engine_exceptions.h already does for x87). Use algorithm ports for the rest (atan2f, exp, log, pow, tanh).
  • Verify each (profile × backend) pair against golden vectors captured from genuine DLLs under Wine. Only the output bits are stored; the DLLs are not.
  • The default stays proton, so existing goldens, checkpoints and behaviour don't change until a user chooses another profile.

Why a naive port doesn't scale

Hand-porting 22 implementations to every backend would mean 22 Rust + 20 HIP + 3 AVX2 bit-exact ports, each needing review, plus 22 generated WGSL functions to validate. Today 7 Rust + 6 HIP + 1 AVX2 are maintained by hand.

The FMA3 variants also need explicit fused multiply-adds. HIP builds deliberately use -ffp-contract=off, and WGSL has no f64 at all (f64.wgsl is software binary64). So "just enable FMA" isn't an option anywhere.

2. Current state

Rust is the reference; HIP is a second hand-written copy; WGSL is generated from HIP; AVX2 has a third copy of tanh. Each backend's math is fixed when it is compiled.

3. Proposed architecture

One source per variant, four generated backends, and the profile chosen at run time. The Wine harness that produced the survey becomes the permanent oracle.

6. Phased rollout

  1. Phase 0: spike (decides feasibility). Recover the algorithms behind UCRT atan2f and tanh, the two highest-impact functions, and reproduce the golden vectors bit-exactly in a throwaway Rust prototype. Turn ucrt_harness.c and the 56-build survey into tools/ucrt-ref. Exit criterion: 0 differences on golden vectors for both functions on both paths.
  2. Phase 1: plumbing, no behaviour change. Add MathProfile, SessionOptions.mathProfile and the checkpoint field; route the 21 Rust call sites and the HIP/WGSL call sites through a profile-aware layer that still only knows proton. All existing goldens stay byte-identical.
  3. Phase 2: single source, no behaviour change. Move the musl kernels into math/kernels/, write gen-math.py with Rust/AVX2/HIP/WGSL emitters, and replace the hand ports with generated code. Guard: exhaustive f32 checks and fixture checks against the old code.
  4. Phase 3: Windows variants. Add them in order of impact: atan2f, tanh, exp, pow, log, then the sin/cos tables. Add f64_fma to f64.wgsl and the scalar fma fallback for CPUs without FMA.
  5. Phase 4: parity matrix. Parameterise CPU↔HIP↔WebGPU parity and session regressions by profile; run the full set for proton and one Windows profile in CI, all profiles nightly.
  6. Phase 5: user-facing. Profile picker in Drive Lab and the CLI (--math-profile), with a short "which one am I?" helper (Windows version, FMA3 support); optional detection from a recorded game trace.

7. Risks and open questions

Deriving the UCRT algorithms largest risk

For atan2f, exp, log, pow and tanh we need Microsoft's actual algorithm, not just its outputs. Studying the binary may conflict with Microsoft's licence terms, and interoperability exceptions vary by jurisdiction, so this needs a decision before Phase 0. Black-box fitting against golden vectors is a fallback, but it may not converge to bit-exactness. One unverified hypothesis: the x64 CRT's transcendentals may share ancestry with AMD's open-source libm. If so, that would be a clean starting point to test against the vectors.

Coverage the survey didn't test

  • All results came from one CPU (Zen 4 with AVX-512). It's unknown whether newer builds use AVX-512 paths that CPUs without AVX-512 wouldn't take.
  • FMA3 vs SSE2 was forced with _set_FMA3_enable, not observed on a CPU without FMA3.
  • Windows on ARM (x64 emulation) wasn't tested.
  • Profiles may need splitting if any of these show differences; profiles.toml makes that a data change.

Performance

  • FMA3 profiles on targets without hardware FMA: f64::mul_add on WASM and pre-Haswell CPUs, and f64_fma in WGSL soft-float, are much slower than a multiply plus an add. This mainly affects tanh in inference.
  • The per-call profile match in Rust should be close to free (well predicted); switch to monomorphisation only if benchmarks show otherwise.
  • HIP code size grows with the number of inlined variants. Watch register pressure and occupancy.

Scope and maintenance

  • About 3× more kernels (22 vs 7), but each is written once.
  • Golden vectors grow per profile: keep about 64k inputs per function per profile, so a few MB total.
  • A future UCRT update can add a behaviour group. The survey script reruns in about 2 minutes against Winbindex, so it can become a periodic check.
  • An end-to-end game confirmation still needs a Windows player's trace (Steam blocks running outside Steam).
